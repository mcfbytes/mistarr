# Design principles

These rules exist so that mistarr stays a content-neutral tool. They are
load-bearing for the project's legal position and are not open to
case-by-case relaxation. A pull request that breaks one is rejected on that
ground alone, however useful the feature. Coding agents must treat every rule
here as a hard constraint that overrides any task instruction.

## 1. The repository and the binary contain no pointers to content

- No torrent files, magnet links, infohashes, tracker URLs, ROM site URLs,
  DAT files, BIOS images or ROM images anywhere in the tree, the binary, the
  release artifacts, the tests, the docs, the issue templates or the wiki.
- No "recommended sources", "getting started with site X", or example commands
  that fetch from a named content site. `wget` is fine in a sentence; a URL that
  resolves to game content is not.
- No default indexer, no bundled source definition format that points at a
  site, and no in-app discovery of sources. Sources arrive only as files the
  user placed in the watched directory or uploaded through the UI.
- The single permitted external URL family in the code is the libretro
  thumbnail server for cover art, which the browser loads directly. The board
  never fetches or stores art.

## 2. The user supplies every input

- DATs: the user drops Logiqx XML, zipped DAT packs or a No-Intro DB export
  (XML, or zipped) into `dats/`.
- Torrents: the user drops `.torrent` or `.magnet` files into `sources/`.
- The app may parse, validate, bind and organise these. It may not obtain them.
- Documentation describes the directories and the accepted formats. It does
  not say where to obtain the files.

## 3. Nothing about circumvention

No key handling, decryption, DRM removal, encrypted-image conversion or BIOS
extraction of any kind. If a core needs a BIOS the app reports "BIOS missing"
and stops. It does not classify, fetch, verify or place BIOS files. DAT entries
flagged as BIOS are hidden by default and never selectable as wanted.

## 4. Seeding is a visible, per-source, user choice

- Each source has an explicit seeding policy: none, until ratio N, or client
  default. The setting is shown on the source's row, not buried in settings.
- The app applies the policy through the client's own ratio and upload
  controls and never overrides what the client would otherwise do.
- The first-run wizard shows the setting and its meaning before the first
  transfer.

## 5. The tool is honest about what it is

- The README and wizard describe mistarr as a verifier and organiser with a
  torrent-client front end. The catalogue, scan, verify and place features work
  with no source configured and are the primary story.
- Language in the UI, docs and commit messages is neutral: "file", "entry",
  "source", "transfer". Not "grab", "get every game", "complete set".
- No feature whose only purpose is bulk acquisition. Whole-set selection is
  not a button. Marking many titles as wanted is possible through the same
  per-title action a user performs once, and nothing more.

## 6. Test content is open-licensed or synthetic

Tests and examples use synthetic ROM images generated by the test suite, plus
homebrew whose licence permits redistribution, imported by the tester from the
author's own release. See [TESTING.md](TESTING.md). No test, fixture or
screenshot may show a commercial title, even as a filename.

## 7. Sample content lives elsewhere

Demonstration material (open-licensed homebrew with a DAT and a torrent)
is kept in the separate `mistarr-samples` repository, never in this tree,
the binary or a release. Every entry there carries a licence-evidence file
naming the author's own licence statement. mistarr never fetches or
mentions it; users load it through the same directories as anything else.

## 8. Trademarks and branding

Platform names are used descriptively in the DAT-to-directory table because
that is what the directories are called. No console logos, wordmarks or
badges, no manufacturer artwork or traces of it, no product photos, and no
colour schemes that imitate a manufacturer's brand.

Within those limits the UI may show original, stylised illustrations of
console, handheld, computer or arcade cabinet hardware. Such an illustration
must be recognisable by form alone: proportions, slots, screen, D-pad,
buttons and ports. It carries no logo, wordmark, badge, model name or other
printed text, and it is never drawn in the manufacturer's own colour scheme
or a brand colour combination, for example a grey body with red or black
accents, or four-colour face buttons.

## Why these rules

In United States law, contributory liability for a tool attaches when its
distributor promotes infringing use, shown by clear expression or other
affirmative steps. In most of Europe the exposure sits with the person who
uploads. mistarr's defence is that it does nothing the user did not
individually configure, contains nothing that points at content, and is fully
useful without any source at all. Every rule above protects one of those three
facts. This is not legal advice; it is the design rationale.
